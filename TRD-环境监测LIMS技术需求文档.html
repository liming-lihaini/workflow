1. 引言与范围

1.1 TRD 与 PRD 的关系

  • PRD 定义「做什么、长什么样、交互如何」（业务功能 + 界面）；
  • TRD（本文件） 定义「怎么建、数据怎么组织、状态怎么流转、接口怎么定、怎么验收」（技术方案 + 验收标准）；
  • PRD 中每个功能点（含优先级 P0/P1/P2）在本文第 5 章对应一节六要素技术实现，并以第 8 章验收用例闭合。

1.2 设计原则

原则落地要求

合规优先不可篡改、资质闸门、质控锁定、授权绑定等硬约束在服务端强制校验，前端仅做体验

2. 总体技术架构

2.1 架构风格

采用前后端分离 + 模块化单体（Modulith）架构：Web 管理端、微信小程序、可视化大屏作为展示层；核心业务能力以领域内聚的 Module 形式组织在统一后端应用内；横切能力（规则引擎、编号引擎、消息中心、审计、公式计算、报表/PDF）下沉为平台支撑组件；监管平台/ERP 通过集成层适配器对接。单实验室规模（≤200 并发）下单应用 + 单 SQLite 文件即可支撑，无 MQ / 无 Redis / 无工作流引擎，部署与运维极简。

2.3 关键架构决策

决策点选择理由
单体 vs 微服务模块化单体起步单实验室规模下降低运维与分布式复杂度；组件边界清晰
流程实现固定状态机（硬编码），不引入工作流引擎流程固定且确定，可穷举迁移+守卫、易单测、零额外中间件
规则引擎自研轻量规则引擎（QLExpress）质控判定/预警规则频繁变更，需动态配置
文件存储服务器本地文件系统（目录只读 + 哈希存证）免对象存储中间件；以文件系统权限 + SHA-256 实现类 WORM 防篡改
缓存/队列弃用 Redis 与 MQ单实验室并发可控；缓存用应用内内存 + SQLite 索引；通知/导出由定时任务/线程池处理
关系数据库SQLite 3（单文件，WAL）零部署、易备份；WAL 支撑读写并发；SQL 标准，可平滑切 MySQL
不可篡改实现审计日志 WORM + 业务数据版本化 + 哈希存证满足 CMA/等保对数据溯源与防篡改的强制要求
SQLite 并发说明：启用 WAL、busy_timeout（如 5s）、连接池单写者串行化关键写路径；单库 ≤200 并发混合读写（以读为主）在 SSD 上可稳定支撑。若未来多实验室/高并发，可平滑切换 MySQL（ORM 层为 MyBatis-Plus，SQL 语法保持标准）。

4. 部署与数据架构

4.1 部署拓扑

区域部署内容说明
内网区（核心）Web 后端（jar + SQLite 文件）、服务器文件系统、定时任务实验室内部网络，与互联网隔离
DMZ / 边界Nginx 网关、微信回调接收、监管平台上报客户端仅暴露必要 HTTPS 端口
外部依赖微信开放平台、短信网关、监管平台、ERP标准协议对接，敏感数据加密传输
合规提示：原始检测数据、现场照片等涉密/敏感数据原则上不出内网；上报监管平台仅传输经脱敏/规范化的监测结果，通道 HTTPS + 字段级加密。

4.2 数据架构

  • 业务库（SQLite）：委托、订单、样品、检测、质控、物资、报告、人员权限等；敏感字段（手机号、身份证、排污许可）AES 加密存储。
  • 文件库（服务器本地文件系统）：现场照片、校准/标物证书、报告 PDF 落盘到 /data/lims/files/，按 年/月/业务类型 分子目录；写入后权限置只读（0444），记录 SHA-256 至 t_file_meta。
  • 审计（独立 SQLite 文件或同库独立表）：操作审计日志，仅 INSERT，无 UPDATE/DELETE；AOP 切面采集（操作人/时间/对象/前后值）。
  • 备份策略：每日全量（SQLite 文件物理拷贝 + 文件系统 rsync 增量）；加密保留 ≥90 天；定期恢复演练。

4.3 不可篡改技术实现

机制实现方式
操作审计日志独立日志库/表，账号仅授予 INSERT；AOP 切面采集，无删除接口
业务数据修改不物理删除；logical_delete + 历史版本表（*_history）保留变更前后值
电子记录完整性关键记录生成哈希（SHA-256）+ 时间戳；可选第三方存证
文件防篡改目录写入后文件权限置只读 + 计算 SHA-256 存 t_file_meta；读取时校验

5.1 委托与采样订单管理P0 · PRD 6.2

5.1.1 功能说明

  • 客户基础档案管理（企业名称/联系人/排污许可编号/开票信息/客户等级）。
  • 委托单创建：常规/监督/应急/信访专项监测分类；录入点位、监测类别、检测项目、执行标准、频次、要求。
  • 报价与合同关联：绑定报价单、合同，记录单价/总价/加急费。
  • 收费对账：收款、发票登记、欠款台账，按客户/订单对账。
  • 技术室（实验室）方法/能力评审（G3）：委托提交后进入「待技术确认」，由技术室评审检测方法适用性、实验室检测能力并出具确认意见，通过后方可生成采样订单（见 5.1.3 委托确认状态机、5.1.6 t_entrust_review）。
  • 由委托一键生成采样订单（拆单），写入订单池（待派单，需「已确认」状态）。

6. 流程设计（端到端 + 关键子流程）

6.1 端到端主流程（委托 → 归档）

① 委托登记→ ①a 技术室确认→ ② 生成采样订单→ ③ 调度派单→ ④ 小程序外勤采样→ ⑤ 扫码收样/分样→ ⑥ 检测+质控→ ⑦ 报告三审→ ⑧ 归档/上报

6.2 关键子流程

6.2.1 派单流程（→ 5.2）

订单池出现「待派单」→ 调度员看板选单 → 分配 负责人/组员/车辆/设备 → 系统校验（资质/冲突/校准有效期） → 通过则置「已派单/执行中」并同步发微信订阅消息；任一校验失败阻断。

6.2.2 外勤采样 + 送检（→ 5.3）

小程序拉取任务 → 填现场参数（时间/GPS 自动）→ 绑现场质控 → 拍照（水印）→ 蓝牙打印条码 → 提交送检 → 实验室收样待办（订阅消息+站内信）。离线表单恢复网络后同步。

6.2.3 收样分样（→ 5.4）

扫条码 → 带出订单信息 → 核验项勾选 → 通过则生成样品记录（检测样派发检测任务、留样入留样库）；拒收登记原因+拍照并通知补采。

6.2.4 检测与质控闭环（→ 5.6）

检测员领任务 → 资质闸门 → 手工录入/Excel 导入 → 公式引擎计算 → 规则引擎质控判定：合格进报告候选；不合格则数据锁定 + 强制异常说明/复测。整批合格方可流转报告编制。

6.2.5 报告三级审核（→ 5.7）

编制生成报告 → 自审（账号确认）→ 审核（复核+意见，可驳回）→ 签发（质控核查结论，可驳回）→ 签发后生成 PDF 落服务器文件系统归档、推送客户、可上报监管。以登录账号 + 审计归属，无图形电子签名。

6.2.6 预警与审批流（→ 5.5）

定时任务扫描：校准/标物/试剂/留样到期、数据超标 → 写预警表 + 同步推送（站内信/微信/短信）。留样销毁、危化品报废走固定审批状态机，记录不可删。

6.2.7 委托技术确认（→ 5.1，G3）

业务员提交委托 → 状态「待技术确认」→ 技术室评审方法适用性/实验室能力并出具确认意见（写 t_entrust_review）→ 通过置「已确认」并触发拆单生成采样订单；不通过「已退回」，修改后重提。

6.2.8 质控计划与能力验证（→ 5.12，G5+G6）

质量负责人编制年度/季度质控计划（t_qc_plan，审批后执行中）→ 按计划登记监控活动（t_qc_activity）并与 5.6 质控判定联动；外部能力验证（t_proficiency_test）、实验室间比对（t_interlab_compare）、重复性试验（t_repeat_test）结果纳入人员/方法能力画像，不合格触发 5.9 资质复核。

11. TRD 自检与审查报告

本章为针对第 5 章各模块「输入 / 数据模型 / 内部逻辑 / 模块间依赖」的系统性自检。审查项已于 11.1 定义，11.2 给出模块输入与依赖关系，11.3 为自检发现与修复清单（均已在本文件中就地修复）。

11.1 审查项定义（四类）

审查维度审查内容（勾选式清单）
一、模块输入完整性①每模块是否明确输入来源（上游表/模块）；②触发条件是否明确；③依赖的前置状态是否已定义；④输入缺失是否会阻断下游。
二、数据模型一致性①接口/规则中引用的表是否已在数据模型定义；②字段命名跨模块一致；③外键引用目标存在且唯一；④状态机枚举值是否全覆盖（枚举 ⊇ 状态机所有状态）。
三、模块内部逻辑性①状态机守卫与业务规则一致；②接口覆盖功能说明全部动作；③数据模型字段足以支撑业务规则与界面；④无自相矛盾表述。
四、模块间依赖性①上游输出是否被下游消费；②共享实体（文件/预警/消息/车辆）是否单一归属定义；③无循环依赖、无孤儿表；④跨模块编号/编码贯穿一致。
